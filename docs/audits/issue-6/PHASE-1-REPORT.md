## Executive findings

1. **The installed baseline is recoverable in full.** At 9:16:59 a.m. CST, both hosted environments contained BVM `1.3.19-vendor-portal.20261116.1411`. All 432 file contents match each other, the accepted #140 ZIP and the BVM subtree of local commit `4b810e1dc9e1cc6ca9d439773d762cc13975b934`. GitHub does not have that commit in the captured mirror. It does have historical lines and later drafts. This identifies the exact baseline for review while leaving cumulative source designation open.
2. **#10/#143 is a confirmed loss of previously accepted behavior.** The Data Tools provider still produces category detail. BVM discards it during normalization and its Vendor Portal renders the aggregate with generic count labels. A controlled fixture reproduced loss at the normalization boundary. An authenticated historical Production source backup places the omission in the October 11 pre-promotion BVM 1.3.5 tree, well before #140. September’s accepted branch is recoverable and still separate.
3. **The original #6 Guest List absence does not describe the captured .1411 source.** Both launchers, the capability and nonce gates, three print modes, report assets and the request registration are present. The historical commit is reachable through many current refs. Complete report output and count parity still need a contained WordPress replay.
4. **Several critical later releases have measurable source continuity.** #5 RC2’s three promoted plugin files, both external workers and the R23 CREATE integration owner match retained evidence. #104’s four functional files match its accepted ZIP. BVM checkout .6 to .1411 differs in vendor, availability and release-marker paths, preserving the ticketing and checkout owners by hash. These findings verify code continuity with historical operational acceptance and leave current workflow replay visible in the matrix.
5. **There is a plausible separate paid-attendance risk.** Retained #143 evidence shows a difference in the paid-presale and paid-door split for the same historical event. The complimentary aggregate agrees. Changes to counts, eligibility, source windows and data after September can each affect that comparison. No finding about payout or a current paid-classification defect is established by that evidence alone.

## Why the losses could recur

- **The deployed artifact could advance while the cumulative source did not.** #10 closed with an explicit unmerged note. Branch history then advanced without the two category-contract owners. The current deployed package is fully reproducible from local Git but its exact commit is absent from the GitHub snapshot. GitHub's default branch is a different lineage. #124 had to reconstruct source from installed copies and draft PRs.
- **Version labels previously mapped to different bytes.** #10 changed runtime under 1.3.1. #88 changed two deployed files under 1.3.13. #5 RC2 accepted another exact 1.3.13 package. The inventory can distinguish content identity, release package and rollback ZIP even when version labels coincide. For release evidence, retain the ZIP hash and the complete content manifest.
- **Issue acceptance and later package qualification covered different surfaces.** #10’s release proved September UI and counts. Current code preserved the aggregate while dropping a field at the provider contract boundary. A test only checking a renderer, version header or plugin load would miss it. #104 and #105 show why environmental acceptance scope needs to stay explicit.
- **Source snapshots alone omit external runtime contracts.** #5 depends on cron, external workers and cache adoption. #38 and show-night performance rely on BVM, Ops, Rentals, Express Bar and real device behavior. Track those identities in the existing release notes.
- **Debug and historical fixtures can age out of the exact-package test path.** The historical reporting fixture pins 1.3.13 and the Agreements fixture assumed legacy dispatch. This audit retained both original failures and narrowly adapted checks. Future regressions need behavior assertions exercised against the extracted artifact with current integrations.

## Required completion rule and mechanical enforcement

Use the existing GitHub repository, PHP tests, package builder and manual transfer/verification tools. Designate a single operational BVM branch after review and start from the verified `4b810e1` installed subtree. Reconcile changes by behavior and owning files with acceptance tests. Preserve legacy and historical refs. A permanent branch name, push, merge or policy change was outside this phase.

1. **Source evidence.** Put approved code and tests in the designated source. Record the full reachable commit on the issue, including every companion change relevant to the claim. Require the release manifest to identify that commit.
2. **Unique complete artifact.** Assign a unique complete BVM release version. Build from the recorded clean tree, retain the package and sorted per-file SHA-256 manifest, and record the package SHA-256 plus relevant companion versions and external scripts.
3. **Required checks.** Use the existing builder and fixture tests on an extraction of the exact ZIP. A small existing-repository validation step can compare the extraction against the recorded commit after documented exclusions, verify version markers and check required release-note fields. Use the current installed-source helper for readback. Preserve rollback source and mode evidence.
4. **Environment acceptance.** Record Local, separately authorized Staging acceptance, and separately authorized Production acceptance for the identical package and composition. Include actual checks passed and explicit unexercised behavior. Retain backups and post-install results under the manual protocol.
5. **Closure evidence.** Use a short GitHub issue template/checklist or a read-only `gh` validation at closure. Require source commit, version, ZIP and manifest SHA-256, test evidence, acceptance and rollback links for completed BVM core issues. Use existing GitHub Actions or existing branch protection when available to require build/test status before merge. A short existing-repo closure check or maintainer checklist is sufficient for acceptance fields. Multiple issues can link the same immutable release. Leave issues waiting on integration or deployment open. Close not-planned or superseded work with its explicit nonimplementation disposition.

No release registry, host, service, enforcement grant or change to the restored manual approval protocol is needed.
