# Future controlled normal-local promotion — plan only

This task performs no promotion. The target source will be the exact green integration commit and its preserved Financial/Staffing ancestry, never the original dirty development branch. Normal installed plugins are deployment copies, not Git worktrees.

1. Record explicit authorization, exact source commit, canonical target basename/path and version inventory. Review the integration report, unresolved historical payables fixture, companion exceptions and migration receipt. Re-run disposable acceptance from that commit before touching normal Local.
2. Preserve exact installed BVM source and the current compatible companion versions as rollback artifacts outside the webroot. Record file counts/digests and restore instructions. Keep existing rollback artifacts and protected stash intact. Investor source patch remains a separately reviewed companion candidate; do not silently include it in BVM replacement.
3. Freeze all staffing/date/time/reschedule writers, including cron, operator/staff actions and integrations. Back up the full WordPress database; additionally retain targeted exports and SHOW CREATE TABLE for assignments, event slots, staffing audit, rollups, posts/postmeta, termmeta/term_taxonomy, staffing templates/roles and relevant options. The complete backup covers any tables enlisted by canonical rescheduling and subscribers. Capture activation list, schema/version settings, row counts and history hashes.
4. Run read-only schema preflight on the authorized target: stock wpdb; InnoDB for all lifecycle transaction tables and financial role metadata tables; expected existing columns/index shapes; duplicate active pair/history counts; orphan assignment identities; valid event/shift windows and role-rate data. Stop for deliberate review on incompatible shapes/engines, active duplicates or unresolved identity problems. Never delete history to make a gate pass.
5. Replace only the canonical installed BVM source from the accepted integration commit while writers remain stopped. Synchronize shared deployment files using an explicit file manifest and preserve mirror/live structural differences; do not copy docs/tests/Git or overwrite independent companion plugins or the legacy vms deployment by inference. Record exact before/after source hashes. Do not deactivate/reactivate solely to trigger migration.
6. Perform normal-local read-only bootstrap/availability acceptance with notification/network containment appropriate to that authorized window. Before migration, lifecycle writes must fail closed and financial labor may report unavailable. This is an expected pre-migration state, not permission to enable writes.
7. As the authorized administrator, run explicit bvmgr_staffing_migrate_lifecycle(). Save result and actual schema/index definitions. Run it again, compare schema and assignment/history rows, and verify idempotence. Migration adds assignment revision, nullable audit assignment/operation identifiers, unique operation index and assignment index. It does not backfill decisions, delete duplicates, settle payroll or synthesize historic audit identities.
8. Compare post-migration receipt to the preflight/backup: InnoDB engines, exact columns/indexes, preserved rows/history, default zero revision on preexisting assignments, no fabricated old operation IDs, duplicate/orphan inventory and no unexpected options/activation changes. DDL is additive and not transactional; recover partial installation forward after inspection.
9. Use isolated synthetic acceptance records only under that future authorization: Proposed/Confirmed/Declined/Canceled and stale revision; reasoned Cancel/Repropose; staff ownership/nonces; atomic audit and overlapping confirmations; Event Plan/ECC/portal agreement; planned and committed labor including override/time changes; paid/zero/refunded/stale/manual financial evidence; Data Tools active/inactive/absent and both orders. Never use real payment or communication actions as a smoke test.
10. Restore writer access only after source, schema, financial/staffing and companion acceptance pass and notifications are deliberately reviewed. Verify cron/locks/guards/test data cleanup; retain the promotion receipt, exact candidate SHA, backups and rollback requirements.

## Rollback constraints

If source acceptance fails, preserve migration/audit evidence and keep staffing writers stopped. Retain additive columns/indexes during source rollback; dropping them destroys provenance and cannot be justified by a file rollback. The prior matrix writer restores known lifecycle gaps, so a code-only rollback is not a safe resumption policy. Prefer a compatible forward fix. Any database restore must deliberately account for post-backup business/audit writes; do not overwrite them with a broad restore by default. Rollback execution needs its own exact approved target/scope within the future promotion task.
