# Site-owned Google Calendar configuration

Phase 4A uses a separate OAuth Web application client owned by each venue. No shared BVM client secret or hosted authorization service is included. A future hosted service would need its own operational ownership, verification, tenant isolation, revocation, availability and privacy review; it is not part of this implementation.

1. In your own Google Cloud project, enable **Google Calendar API**. Configure Google Auth Platform branding, audience and consent information. For first acceptance choose **External / Testing**, and add only an authorized non-production Google test account as a test user. Use an Internal audience only when the venue's Workspace organization and intended users qualify.
2. Create an OAuth client of type **Web application**. Request precisely `openid` and `https://www.googleapis.com/auth/calendar.app.created`. The callback rejects unexpected additional granted scopes, including broad Calendar permissions. Use a dedicated client/project rather than reusing a previously broadly authorized integration. No Google Tasks, calendar-list, email or profile scope is requested.
3. Register the **exact redirect URI displayed in Users/Profile → BVM Tasks Google Calendar** (the submenu appears under Users/Profile). For a venue at `https://venue.example`, the URI is `https://venue.example/wp-admin/admin-post.php?action=bvmgr_google_callback`. Scheme, host, port, path and query must match. No JavaScript origin is needed for this server-side flow.
4. Supply these constants before WordPress loads, through environment-backed `wp-config.php` configuration. Never put values in the plugin, a browser form, a task, a log or an email:

   ```php
   define('BVM_GOOGLE_CLIENT_ID', getenv('BVM_GOOGLE_CLIENT_ID'));
   define('BVM_GOOGLE_CLIENT_SECRET', getenv('BVM_GOOGLE_CLIENT_SECRET'));
   define('BVM_GOOGLE_TOKEN_KEY', getenv('BVM_GOOGLE_TOKEN_KEY'));
   ```

   The token key must be a securely generated, base64-encoded **32-byte random key** available only to the PHP server. Store it separately from database backups and plugin files; sodium authenticated encryption is required. Do not reuse the client secret as this key. The UI reports only whether configuration is usable.
5. Ensure Staff Tasks' explicit reliability setup is complete. Its existing `vms_tasks_notifications_tick` cron runs every fifteen minutes; the Google worker is attached to that hook without adding events on page reads. The site's external cron must continue processing due WordPress cron events. Operators can also explicitly run `bvmgr_google_tick()` through trusted local WP-CLI. Work is limited to twenty target attempts and a soft 45-second worker budget per invocation; a slow in-flight HTTP request may extend this budget. Large backlogs drain over repeated runs.
6. Sign in as the actual eligible BVM task assignee, open the Google Calendar screen and select **Connect Google account**. Complete Google consent in that same WordPress browser session. The worker creates the dedicated calendar and selects current work; **Sync Now** requests immediate reconciliation for the signed-in person's target. Administrators see connection health and counts but cannot read credentials or connect on someone else's behalf through this screen.

The normal Local URL is currently `https://serenaderange.local`. Google's web-client redirect rules do not accept arbitrary `.local` suffixes. Do not register that URI and assume it will work. Controlled real-account acceptance needs an authenticated test instance served on an allowed origin: for example `http://localhost:8799`, with both WordPress home/site URLs consistently overridden in the test harness, and the exact redirect `http://localhost:8799/wp-admin/admin-post.php?action=bvmgr_google_callback`. Google permits HTTP for localhost; production and other hosts use HTTPS. The current integration permits that loopback exception only when WordPress itself is configured on the loopback HTTP origin. Preserve the same host/session through start and callback. No loopback server or real-account session was left running by this task.

Google's External / Testing refresh tokens expire after seven days for these scopes. That is expected test behavior and must lead to reconnect status. Production use requires appropriate publishing/verification according to Google Auth Platform's current project requirements. Do not confuse successful testing consent with completed production verification.

## Operations and recovery

- **Refresh and rotation:** access tokens refresh only during explicit OAuth operations or worker execution. A returned replacement refresh token is encrypted and persisted before subsequent API work. Reconnect replaces tokens for the same Google `sub`; email is never the connection key. A different Google account cannot silently replace the existing account.
- **Client changes:** changing the client ID requires reconnect. Existing app-created calendars may be inaccessible to a different Google project. Preserve/restore the original venue client for reconnect; changing Google projects is a separate explicit migration, not a calendar-name search.
- **Encryption-key loss/rotation:** a lost key fails closed and requires each person to reconnect. Preserve the old key securely until rotation is complete. A controlled rotation can disconnect connections locally, change the key, then reconnect each original Google account; the stored subject and calendar identity survive. Never delete the state option as a shortcut, because it contains deduplication identities.
- **Calendar creation uncertainty:** the local creation intent is saved before `calendars.insert`. Google does not support supplying a calendar ID to that endpoint, and the selected scope cannot list a user's calendars. A timeout/process crash therefore enters `creation_uncertain`. Find the created **BVM Tasks** calendar in Google's UI and paste its calendar ID into **Recover existing BVM calendar**. BVM checks the exact application marker and narrow-scope access. It does not search by title or auto-create another calendar. If the request demonstrably failed before creation, support must resolve that uncertainty with evidence; there is intentionally no blind reset button for ambiguous attempts.
- **Rejected creation:** a definitive 400/401/403/404/429 rejection exposes **Retry rejected calendar creation**. Resolve authorization/configuration first. Each retry changes the durable state once; replay cannot create another calendar.
- **Deleted calendar:** a successful worker check detecting 404/410 enters `missing`. Recover an existing matching calendar, or explicitly check the confirmation box and request **Replace confirmed missing calendar**. BVM rechecks the old ID and permits one new creation intent. An uncertain replacement follows the same recovery rule. No calendar deletion action is implemented.
- **Missing event / external edit:** Sync Now and hourly worker reconciliation retrieve only known dedicated-calendar event IDs. Missing events reuse the deterministic ID; BVM-owned fields are reconciled with ETag-conditional patches. Matching fields produce no write. Reminders, colors and unrelated private properties survive. Tombstone restore behavior remains part of mandatory real-Google acceptance.
- **Disconnect:** synchronization stops, pending OAuth state is removed and usable local credentials are erased. Calendar identity and historical events remain. Local disconnect does not call project-wide Google revocation, which can affect other clients in a shared project. A person can additionally revoke the dedicated project from Google's account settings; subsequent requests stop in reconnect state. No historical calendar/event deletion occurs.
- **Logging:** BVM stores safe state/HTTP codes only. Configure reverse-proxy/access logs to omit/redact OAuth callback query strings. Exclude these Google requests from any third-party HTTP request/response debug logger; WordPress HTTP transport hooks are trusted server extension points and receive transport arguments. Do not use browser token inspectors or tokeninfo URLs for acceptance. Callback completion immediately redirects to a clean status URL with no-referrer/no-cache headers.
