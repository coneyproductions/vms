## 3. Trialware and Locked Features

The reviewer says WordPress.org-hosted plugin code must be fully functional and must not contain locked built-in functionality.

- Built-in features must not be locked, disabled, or limited by a license key, trial period, usage limit, time limit, quota, or similar restriction.
- The reviewer says that even code included "just in case the user upgrades" is not allowed if it keeps built-in features locked locally.
- The plugin may mention that additional features are available through a separate plugin, but the code hosted on WordPress.org must itself remain free and fully functional.
- Legitimate external services are allowed only when they perform actual processing on external servers, provide functionality that cannot be done locally by the plugin, and are clearly documented in the readme with Terms of Use and Privacy Policy links.
- A license-check-only unlock mechanism is explicitly described as non-compliant.
- The reviewer instructs the author to remove license checks and similar gating for built-in code, remove or fully enable locked built-in features, and ensure any external services are compliant and clearly documented.
- The reviewer also states that WordPress.org is not a marketplace. If extra paid functionality is offered, that code must be hosted elsewhere and not included in the WordPress.org plugin package.

## 5. Nonces and User Permissions

The reviewer says any user-triggered request that uses `$_GET`, `$_POST`, or `$_REQUEST` to modify data or perform sensitive operations must validate a nonce and, where applicable, verify user permissions or object-level authorization.

- Nonces can be created with `wp_nonce_field()`, `wp_nonce_url()`, or `wp_create_nonce()`.
- If a nonce needs to reach JavaScript, the reviewer recommends passing it through `wp_localize_script()`.
- Nonces can be checked with `check_admin_referer()`, `check_ajax_referer()`, or `wp_verify_nonce()`.
- Permissions should be verified with functions such as `current_user_can()` when the action is role-restricted.
- The reviewer warns that skipping nonce and permission checks can allow unauthorized callers to reach AJAX or other sensitive handlers.

The email does not list plugin-specific file examples in this subsection; it states the requirement generally and instructs the author to search for all similar request handlers.

## 6. Input Sanitization

### Request Globals

The reviewer says inputs from `$_GET`, `$_POST`, `$_REQUEST`, `$_COOKIE`, `$_SERVER`, and `$_SESSION` must be sanitized as early as possible, using the most restrictive function that fits the expected content.

- Example sanitizers named in the email include `sanitize_text_field()`, `sanitize_email()`, `esc_url_raw()`, `sanitize_key()`, and `absint()`.
- The reviewer says not to trust any input unless the plugin cleaned it itself.

### Uploaded-file MIME trust

The reviewer says the file `type` value supplied in `$_FILES` is requester-controlled and must not be trusted. The email specifically recommends deriving type information from the file itself with `wp_check_filetype()`.

Plugin-specific examples:

- `includes/portal/vendor-tax-profile.php:120` `$type = isset($_FILES['vms_w9_upload']['type']) ? (string) $_FILES['vms_w9_upload']['type'] : '';`

- `includes/admin/tax-profile-admin-metabox.php:110` `$type = isset($_FILES['vms_w9_upload']['type']) ? (string) $_FILES['vms_w9_upload']['type'] : '';`

### Server, Cookie, and Session Values

Plugin-specific examples shown in the email include:

### Using Escaping as Sanitization

The reviewer explicitly says escape functions are not sanitizers and must not be treated as such. The stated reason is that escape functions serve a different purpose, are often filterable, and can become unsafe if another plugin changes their behavior. The reviewer says data should be sanitized first and escaped later when output.

Plugin-specific examples shown in the email include:

- `includes/cpt/ratings.php:350` `value="<?php echo isset($_POST['vms_reviewer_name']) ? esc_attr($_POST['vms_reviewer_name']) : ''; ?>"` `-----> esc_attr($_POST['vms_reviewer_name'])`
- `includes/helpers.php:4184` `echo '<input type="hidden" name="redirect_to" value="' . esc_attr(wp_unslash($_SERVER['REQUEST_URI'])) . '">';` `-----> esc_attr(wp_unslash($_SERVER['REQUEST_URI']))`
- `includes/cpt/ratings.php:357` `value="<?php echo isset($_POST['vms_reviewer_email']) ? esc_attr($_POST['vms_reviewer_email']) : ''; ?>"` `-----> esc_attr($_POST['vms_reviewer_email'])`

## 7. Output Escaping

The reviewer says output should be escaped as late as possible, using the most restrictive function that matches the output context.

- URLs: `esc_url()`
- HTML attributes: `esc_attr()`
- Text inside HTML tags: `esc_html()`
- Raw HTML: `wp_kses()` or `wp_kses_post()`

The reviewer also says that when outputting JSON, `wp_json_encode()` should be used and the plugin should avoid options that effectively bypass safe escaping expectations.

Plugin-specific example shown in the email:

- `includes/public/event-details.php:669` `$json = wp_json_encode($schema, JSON_UNESCAPED_SLASHES | JSON_UNESCAPED_UNICODE);`

The reviewer says Plugin Check can help check escaping-related findings.

- The guidance applies to functions, classes, globals, namespaces, `define()` constants, stored-option or metadata keys, shortcodes, post types, menu pages, registered scripts, localized objects, AJAX actions, and similar declarations.

- The reviewer notes that WordPress 6.9 offers a standardized template enhancement output buffer for whole-response transformations.
